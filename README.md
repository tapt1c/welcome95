# Welcome95

Нативный прототип экрана приветствия в стиле Windows XP для Windows 95.
Один пользователь, без переключения пользователей. C89, ANSI Win32, GDI,
без .NET, браузера и сторонних DLL.

**Статус:** EXE собран, формат и импорты проверены автоматически. Под Wine64 прошли
35 проверок настоящих окон: размещение полей, восстановление диалога, верхний
порядок и сохранение фокуса. Межпроцессная интеграция при настоящем входе ещё
требует проверки в Windows 95. Это экспериментальная интеграция.

## Использование

1. Скопируйте `build/welcome95.exe` в постоянную локальную папку Windows 95,
   например `C:\WELCOME95`. Не перемещайте EXE после включения.
2. Запустите EXE без параметров: откроются настройки.
3. Нажмите **Preview** для безопасного предпросмотра. Кнопка **Finish preview**
   закроет его через одну секунду. Предпросмотр не меняет автозапуск.
4. Нажмите **Enable** и перезагрузите Windows. **Disable** удаляет записи
   автозапуска, принадлежащие этой копии программы, и закрывает её экран.
5. На экране входа отображаются сохранённое имя пользователя, поле пароля и OK.
   Для возврата полного штатного окна нажмите **Windows dialog** внизу справа.
   В предпросмотре поле отключено и не принимает пароль.

Интерфейс первой версии на английском: это позволяет использовать один ANSI EXE
на разных локализациях Windows 95 без зависимости от конкретной кодовой страницы.

## Как устроен вход

- `HKLM\Software\Microsoft\Windows\CurrentVersion\RunServices`, значение
  `Welcome95`, запускает `"полный путь к EXE" /welcome` на этапе служб Windows 9x.
- Полноэкранное окно имеет `WS_EX_TOPMOST`, не имеет рамки и игнорирует
  `WM_CLOSE` и системные команды закрытия/сворачивания. Esc и Alt+F4 перехватываются
  временными глобальными горячими клавишами, чтобы не отменять и штатный вход.
- Настоящий диалог Windows остаётся владельцем своего поля `ES_PASSWORD` и OK:
  их родитель, идентификаторы, обработчики и текст пароля не меняются.
  У диалога убирается рамка, остальные элементы скрываются, а его область окна
  обрезается до двух прямоугольников поля и OK. Промежуток между ними прозрачен
  для рисования и мыши. В результате поле выглядит частью экрана приветствия,
  но пароль принимает и проверяет сама Windows. Чужой процесс не подклассируется,
  код в него не внедряется; пароль не читается, не копируется и не сохраняется.
- Из обычного поля имени читается только сохранённое имя пользователя.
  Поле имени скрывается: переключения пользователей нет. Если имя пустое,
  диалог неподдерживаемый либо перехват Esc/Alt+F4 недоступен, остаётся полное
  штатное окно, чтобы не потерять возможность входа.
- Каждые 100 мс верхнее положение экрана восстанавливается без смены фокуса.
  Реальные поле/OK и принадлежащие окну входа сообщения об ошибках остаются выше
  фона, чтобы можно было исправить пароль. Таймер не фокусирует поле повторно.
- `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`, значение `Welcome95`,
  запускает `/session-ready` после перехода Windows к пользовательскому сеансу.
  Сигнал именованного события запускает задержку не менее 1000 мс, затем экран
  закрывается. Таймер опрашивает состояние с интервалом 100 мс.
- Никаких изменений `SYSTEM.INI`, `WIN.INI`, сетевого провайдера или паролей.

### Границы первой версии

`RunServices` — ранний асинхронный запуск, а не синхронный перехват входа:
**появление экрана раньше стандартного диалога пока не гарантируется**.
Потребуется проверка на нужном выпуске Windows 95 и сетевом клиенте.

`Run` означает начало пользовательского сеанса, **не подтверждение успешной
аутентификации**. В Windows 95 отмена штатного входа тоже может открыть рабочий
стол; в таком случае экран также закроется через секунду. Ошибочный пароль,
который оставляет пользователя в диалоге, не должен давать сигнал закрытия.

Поиск окна входа эвристический: первый видимый диалог `#32770` с полем пароля.
Встроенный вид поддерживает простую форму: два Edit (имя и пароль), OK,
необязательные Cancel и статические подписи. Формы с доменом, флажками и другими
параметрами сохраняют штатный вид. Другой диалог имени/пароля на этом этапе
может быть ошибочно принят за окно входа; сетевые клиенты требуют проверки.

Для встроенного вида исходные рамка, область, размеры, позиции, видимость
элементов и состояние Cancel сохраняются и восстанавливаются при штатном выходе,
ошибке размещения или нажатии Windows dialog. Уже скрытый самой Windows диалог
не должен открываться заново. Принудительное завершение процесса не позволяет
выполнить восстановление: при таком сбое может потребоваться перезагрузка.

Поверх обычных окон, включая другие topmost-окна и обычные системные диалоги,
экран возвращается с интервалом таймера. Приоритет не является атомарным:
другое окно может кратковременно появиться до следующего тика. Нельзя гарантировать
рисование поверх меню Ctrl+Alt+Del, критических системных экранов или полноэкранного
DOS. Принудительное завершение не блокируется. Это оформление входа, не средство
ограничения доступа. Повторный вход без перезагрузки не поддерживается.

## Сборка в Linux

Нужны GNU Make и компилятор `i686-w64-mingw32-gcc`:

```sh
# Debian/Ubuntu, при наличии прав администратора:
apt-get install gcc-mingw-w64-i686 make
sh tools/build.sh
python3 tests/check_pe.py build/welcome95.exe
```

В подготовленной облачной среде `tools/build.sh` также находит компилятор в
`/workspace/.tools/mingw`. Итог: `build/welcome95.exe`.

Сборка намеренно не использует современный CRT. Собственная точка входа вызывает
`WinMain` и `ExitProcess`; импортируются только функции четырёх системных DLL.
Заголовок PE задаёт x86, GUI и Windows/subsystem 4.0. Компиляция с `-Werror`.
`tests/check_pe.py` проверяет реальный бинарный файл и запрещает непроверенные
импорты, CRT, .NET и TLS-инициализацию. Это **не заменяет запуск на Windows 95**.

План проверки на целевой системе и восстановление: [docs/TESTING.md](docs/TESTING.md).
Тесты реальных Win32-окон: `sh tools/build.sh test-helper`, затем запустить
`build/native_logon_test.exe` в тестовой Windows. Они создают синтетический диалог,
не меняют реестр и записывают результат в `native-logon-test.log` текущей папки.
32-битный тест для Windows 95 пока только скомпилирован. Его 64-битный вариант
и тест приоритета окон исполнены под Wine64: все 35 проверок прошли.

Для повторения оконных тестов в Linux нужны Wine64, Xvfb и x64 MinGW:

```sh
# Debian/Ubuntu, с правами администратора:
apt-get install wine wine64 xvfb gcc-mingw-w64-x86-64
sh tools/test-wine.sh
```

В подготовленной облачной среде скрипт использует сохранённые инструменты
из `/workspace/.tools/win-tests`. Он запускает отдельный Xvfb без TCP и отдельный
профиль Wine; персональный профиль Wine и реестр Windows не используются.
Системная песочница должна разрешать локальные сокеты Wine/Xvfb.
